From working demo to a tool a clinic can run every day

The demo proves the mechanism. What it doesn't yet have is the shape of a product: nothing validates a code before you see it, nothing carries an encounter past a browser tab, and two-thirds of what you pay per claim buys a transcript the claim never uses.

01 Where it stands

An honest read of the app on claude/ruby-health-mvp-06h6qn before proposing changes to it.

The build is further along than a prototype usually gets. The API key never reaches the browser, every model call is a forced tool call rather than parsed prose, claim population is deliberately deterministic with no model in the loop, and the review lock means nothing is ever presented as final. Those are the right instincts and this plan keeps all of them.

Three structural things separate it from something a clinic could use on a Tuesday morning:

Trust

Nothing checks the model's work

Every ICD-10 and CPT code on the screen is free-generated text. No code is checked against a real code set, no quote is checked against the transcript it claims to come from, and the confidence dot is the same model grading its own answer. A reviewer has no way to tell a solid code from an invented one except by knowing the answer already — which defeats the product.

Shape

The unit of work is one encounter; a clinic's unit is a day

A practice seeing 6–10 patients runs this six to ten times, and each run starts from an empty page with no memory of the last. There is no worklist, no status, no "what still needs me." State lives in sessionStorage, so closing the tab ends the day's work.

Economics

The most expensive call produces nothing the claim needs

Transcript cleanup regenerates the entire transcript as output tokens — 62% of per-claim cost — to produce a punctuated document that the claim never consumes. Extraction reads it, but extraction did fine without it.

Worth keeping

The brand palette work, the sidebar, the code-as-insight-card layout, and the recording-state machine are all good and this plan builds on them rather than replacing them. The rebuild below is about what the screens contain, not how they look.

02 The cost correction

The production cost model budgets $1–3 per claim for LLM work. The measured pipeline is around $0.036. That gap is the most consequential number in this plan, because it changes which model you can afford.

Here is where money actually goes today, for a ten-minute encounter (~1,700 tokens of transcript) on claude-sonnet-5:

Output tokens are the bill, not input

71% of the cost is output. That inverts the usual instinct to trim prompts: shaving the system prompt saves fractions of a cent, while the cleanup step regenerating a 1,700-token transcript costs more than the rest of the pipeline combined. Every efficiency move in this plan targets output.

Prompt caching is not saving you anything

The static prefixes measure roughly 390–500 tokens per call (system prompt plus tool schema). Sonnet 5 will not cache a prefix under 1,024 tokens — it fails silently, with no error and cache_creation_input_tokens: 0. The production plan lists prompt caching as the biggest cost lever; at these sizes it is currently a no-op.

The reframe

Caching isn't a cost lever for this workload — it's what lets you afford a much larger prompt. A 2,500-token block of coding guidance (E/M decision-making rules, specificity requirements, worked examples) costs about $0.0005 per claim to read from cache. Buy accuracy with it. That is the same change appearing in the accuracy section below, which is the point: here the cheap fix and the accurate fix are one fix.

So run coding on Opus 5. Restructuring the pipeline pays for the most capable model outright: you get better coding judgment than today at roughly today's cost. Coding accuracy is the entire product — a denied claim costs a practice far more than every model call that produced it.

Second-order effect

At three cents a claim, a 50-encounter evaluation run costs about $1.50. That makes a real accuracy eval suite — the thing missing from every version of this plan so far — something you can run on every prompt change without thinking about it.

One model call per encounter. Facts never round-trip. Validation, confidence scoring, and the scrub are deterministic code — no tokens, no latency, and they behave the same way every time.

Merge extraction and coding into one call

One request, one tool schema carrying both facts and suggestions. This removes the facts round-trip, one system prompt, and one tool schema, and it lets the model reason from transcript to code in a single pass rather than from a lossy summary of the transcript.

The UI does not have to change to match. Facts and codes stay separate on screen and stay independently editable — one call can populate two panels. What you give up is per-step model routing (extraction on something cheap, coding on something strong); that trade is worth it, because extraction is the easy half and merging saves more than routing would.

Take cleanup off the claim path

Cleanup exists because dictation arrives unpunctuated and those run-on fragments end up quoted in the claim's medical-necessity field. That is a real problem with a cheaper fix: instruct the merged call to punctuate the quotes it extracts. It is already selecting them — it can select them cleanly. The full readable note is a separate concern, so keep the button for it as an on-demand action for the chart, not a required step for the claim.

Never pay twice for the same input

Hash the input to each stage and cache the result. If a reviewer edits one symptom chip and re-runs coding, only coding re-runs; if they change nothing and click again, it costs nothing. For a system run repeatedly against near-identical inputs, this is a larger real-world saving than any prompt tuning, and it also removes the accidental-double-click cost.

Cache the guidance prefix, at one hour

Put the coding guidance block behind an explicit cache_control breakpoint at the end of the shared prefix, never after the transcript — the transcript differs every time, and a breakpoint after it writes a cache entry nobody ever reads. Use the one-hour TTL: a clinic generates a claim every thirty to sixty minutes, so a five-minute entry is always cold by the next one.

Be honest about the break-even

A one-hour cache write costs 2× base input. At three claims an hour it pays for itself; at one claim an hour it does not. Instrument cache_read_input_tokens and check real numbers before assuming the win. If a clinic's rhythm is too sparse, the merged call alone still delivers most of the saving — and an end-of-day batch run keeps the cache hot for every claim while qualifying for the Batch API's 50% discount, which suits how billing actually works.

Housekeeping that blocks the above

  • @anthropic-ai/sdk is pinned at ^0.32.1, well behind current. Upgrade before relying on top-level cache_control, output_config.effort, or adaptive thinking, and re-verify against the changelog.
  • Keep the ANTHROPIC_MODEL environment override — it is what will let you A/B a model against the eval suite without a deploy.
  • Log usage on every call. Cost per claim is a number you should be able to look up, not re-derive.

04 Accuracy

The demo asks a reviewer to trust codes that nothing has checked. Most of what fixes that is deterministic code, not better prompting.

Bug

Every service line points at the first diagnosis

populateClaim.js sets diagnosisPointers: diagnoses[0].pointer for every CPT line. On a visit with a sore throat and a medication refill, the strep test points at whichever diagnosis happened to sort first. Mislinked pointers are a straightforward denial, and this would ship one on any multi-problem encounter.

Fix Add supportingDiagnoses: string[] to each CPT suggestion in the tool schema — the model already knows which diagnosis justifies which service, it is just never asked. Map those to pointer letters in populateClaim. Cap diagnoses at twelve (A–L) per CMS-1500 and surface an error past that rather than running off the end of the alphabet.
Gap

Codes are never checked against a code set

A plausible-looking code that was retired in 2024, or never existed, looks identical on screen to a correct one.

Fix ICD-10-CM is published free by CMS — load the annual release and make validity a hash lookup. Any code not in the set is blocked from the claim, not merely flagged. CPT is AMA-copyrighted and needs a paid license for commercial use; see the open decisions below.
Gap

Quotes are not verified to be quotes

medicalNecessityLanguage is presented as direct quotation and flows into the claim, but nothing confirms the text appears in the transcript. A paraphrase that drifts is a medical-necessity attestation you cannot support in an audit.

Fix Normalized substring match against the transcript, with a token-overlap fallback. Anything that fails gets relabeled "paraphrased" in the UI instead of silently passing as a quote. Costs nothing and runs in milliseconds.
Gap

Confidence is self-reported

The model that wrote the code also rates its own certainty. That number cannot be used to decide what a human reviews, which is the only thing confidence is for.

Fix Compute it from signals you can check: the code exists in the code set; the supporting quote verified; the ICD code is specific rather than an "unspecified" variant; the model flagged ambiguity in its rationale. Keep the model's self-assessment as one input among several, not the output.
Gap

Nothing encodes how E/M levels are chosen

99213 versus 99214 is where a practice's revenue and its denial risk both live, and the prompt says nothing about how that call is made. Right now the level is a guess.

Fix This is what the cached prefix is for. Encode the 2021 office-visit guidelines — level by medical decision-making complexity (problems addressed, data reviewed, risk) or by total time — plus worked examples. Ask the model to state which criterion it applied and show that reasoning on the code card, so a reviewer can check the logic rather than the verdict.
Gap

There is no scrub, which is the differentiator

The one-pager sells "automated claims scrubbing." The app has none — it populates a template and calls it reviewed.

Fix A deterministic pre-submission checklist: every service line links to at least one diagnosis; every code validates; no unspecified ICD code where a specific one is available; required CMS-1500 fields present; NPI well-formed; date of service present and sane. Zero tokens, and it is the screen that makes a biller believe the product.
Gap

No evaluation set, so no accuracy claim is testable

Every prompt change so far has been verified by looking at it. There is no way to know whether a change to the coding prompt made things better or quietly worse.

Fix Build 30–50 synthetic encounters with known-correct codes, spanning the common cases and a few deliberately ambiguous ones. Score code-set validity, primary ICD match, E/M level match, and quote grounding. Run it before and after every prompt change. At $1.50 a run there is no reason not to. This is the single highest-value item in the plan — without it, "more accurate" is an opinion.

05 Workflow

The demo asks the user to drive four tabs and press four buttons for one encounter. The pilot should ask for attention only where attention is worth something.

Automation was the wrong thing to remove

The auto-cascade got cut because it yanked the user between tabs mid-thought. That objection was right — but the fix removed automation along with the navigation-stealing, and what's left is a workflow where every step needs a deliberate click even though the steps always run in the same order.

Run automatically, never navigate. When recording stops, the pipeline runs on its own. Progress shows in place — in the sidebar, on the worklist row — and the user lands wherever they choose, whenever they choose. Full control over where they are; no manual labor to get the work done. That gets back what the cascade was for without reintroducing what made it unpleasant.

The day is the unit, not the encounter

The screen that is missing is the one a biller would actually live in: today's encounters as a list, each with a state and a reason it is in that state.

StateMeansWhat the user does
RecordingCapture in progressNothing
DraftingPipeline runningNothing — go see the next patient
Needs reviewScrub found something, or a code scored lowResolve the flagged items only
ReadyClean scrub, reviewer signed offNothing until submission exists
HeldMissing information the encounter can't supplyNote why; comes back tomorrow

Review by exception

A reviewer reading every field of every claim is the manual process the product is meant to replace. The review screen should open with what needs attention — "2 items need you: an unvalidated CPT code, a diagnosis with no supporting quote" — and let everything that passed stay collapsed and skimmable. Confidence scoring only earns its keep if it decides what surfaces.

Persistence

sessionStorage goes when the tab does. A pilot needs encounters that survive a browser crash and a lunch break: Postgres or SQLite behind the existing endpoints, one row per encounter, with the pipeline output stored as structured JSON. Keep synthetic data only until the compliance phase — the moment real PHI touches this, encryption at rest, audit logging, and a signed BAA stop being optional, and that is a separate phase with its own gate.

06 Interface

The visual language is right. What changes is what the screens have to say — and tabs are the wrong container for a review that is mostly about exceptions.

Worklist becomes home

Sidebar navigation stays. The first screen becomes today's encounters, each row a patient reference, time, state pill, and a count of unresolved flags. A primary record action sits at the top. Opening a row goes to that encounter; finishing one returns here. This one screen is what makes the tool feel like software a practice runs rather than a demo someone shows.

Tabs become one review surface

Four tabs hide state — you cannot see from the Codes tab that the claim has an unlinked service line. Replace them with a single scrolling review page, sectioned as transcript / facts / codes / claim, with a sticky attention summary at the top and anchors in the sidebar for jumping. Everything visible at once, in the order the work happens, with the exceptions pulled to the top.

What each card has to carry now

  • Code card — keep the existing layout, add a validation badge (in code set / not found), the computed confidence rather than the model's, the E/M criterion when it applies, and the supporting quote rendered as a quote with a marker for whether it verified against the transcript.
  • Fact chips — keep. Add a quiet indicator on medical-necessity quotes that failed grounding, so a paraphrase never passes for a quotation.
  • Claim — show the diagnosis-pointer mapping visibly, since it is now real data rather than always "A", and it is the thing a biller checks first.
  • Scrub panel — new, and the last thing before Ready. Each check passes or explains itself in one line. This is the screen that sells the product.

Recording, kept

The push-to-talk and lock state machine, the timer, and the waveform are good and stay as they are. The one change: when recording stops, the pipeline starts on its own, and the encounter appears on the worklist as Drafting — the clinician can walk away.

07 Build order

Ordered so that each phase is independently useful and nothing is built on a data model that is still moving. Sizes are relative, not calendar estimates.

P0

Correctness on what already exists

Small · no new concepts
  • Per-CPT diagnosis pointers; twelve-diagnosis cap with a real error past it.
  • Transcript grounding check on every necessity quote.
  • Upgrade @anthropic-ai/sdk; log usage on every call.
  • Measure real token counts with count_tokens and replace the estimates in section 02.

Done when  a two-problem encounter produces correctly linked service lines, and you can state your per-claim cost from logs rather than arithmetic.

P1

Evaluation set

Small · unblocks judging everything after it
  • 30–50 synthetic encounters with known-correct codes, including ambiguous ones.
  • Scorer: code-set validity, primary ICD match, E/M level match, quote grounding.
  • One command, a printed scorecard, results committed so runs are comparable.

Done when  you have a baseline score for today's pipeline. Every later phase is measured against it.

P2

Pipeline rebuild

Medium · settles the data model
  • Merge extraction and coding; punctuate quotes in-place; retire cleanup from the claim path.
  • Cached guidance prefix with the E/M rules and worked examples, at one-hour TTL.
  • Move to Opus 5 and tune effort against the eval suite.
  • Content-hash memoization per stage.

Done when  eval score is at or above baseline, cost per claim is down, and cache_read_input_tokens is non-zero on the second claim in an hour. UI work can start here — the data model is now fixed.

P3

Validation, confidence, scrub

Medium · mostly deterministic code
  • ICD-10-CM code set loaded; invalid codes blocked from claims.
  • Computed confidence replacing the self-reported field.
  • Scrub checklist as a real gate before Ready.

Done when  no invented code can reach a claim, and every scrub failure names what to fix.

P4

Workflow and persistence

Medium
  • Storage behind the existing endpoints; one record per encounter.
  • Encounter states; pipeline runs automatically on recording stop, without navigating.
  • Worklist as the home screen.

Done when  you can record three encounters back to back, close the browser, reopen it, and find all three with correct states.

P5

Review-by-exception interface

Medium · the "feel" phase
  • Tabs collapse into one review surface with a sticky attention summary.
  • Code cards carry validation, computed confidence, E/M criterion, grounded quotes.
  • Scrub panel; visible diagnosis-pointer mapping.

Done when  a clean encounter can be reviewed and marked Ready without reading the full transcript, and a flawed one shows you exactly what is wrong first.

P6

Pilot readiness

Small · gate, not a build
  • Full eval run and a written accuracy statement — what it gets right, where it does not.
  • Cost-per-claim dashboard from logged usage.
  • Written scope of what the pilot does and does not do, for the design partner.

Done when  a physician can use it on synthetic encounters unaided, and you can answer "how accurate is it" with a number. Real PHI stays behind the compliance phase, which starts here and is a separate plan.

08 Open decisions

Things this plan assumes, and the ones that need your call before the phase that depends on them.

CPT licensing — blocks P3

CPT is AMA copyright, and validating or distributing the code set commercially needs a paid license. ICD-10-CM and HCPCS Level II are free from CMS. For a pilot you can validate ICD-10 fully and hand-maintain the small set of office-visit E/M codes, but shipping CPT validation to a customer needs the license sorted. Confirm the terms with counsel and budget for it — it belongs in the cost model alongside Stedi.

Whether the pilot submits anything

This plan stops at a scrubbed, review-complete claim. Stedi integration and real submission are a separate phase, and they arrive together with the compliance work because a submitted claim carries real PHI by definition. Worth deciding early: does the design partner want a tool that drafts claims their biller then keys in, or one that submits? The first is a much shorter path to being useful.

Assumptions in the cost math

  • ~1,700-token transcript per encounter (roughly ten minutes of speech). A long specialist visit could be three times that, and cost scales close to linearly.
  • Token counts estimated from prompt and schema bytes, not measured — P0 replaces them.
  • Opus 5 output includes adaptive thinking, which is why that row is a range rather than a figure.

What this plan deliberately leaves out

Multi-tenancy, EHR integration, eligibility checking, denial-reason ingestion via 835 remittance, and everything in the HIPAA infrastructure phase. Each is real and none belongs before a design partner has confirmed the core loop is worth their time.
